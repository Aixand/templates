# Workspace products and portable installation

Revision 2 adds a schema-2 workspace beside the existing schema-1 profiles.
Existing configurations, packages, and source-managed installations continue
through the revision-1 adapter. Do not rewrite receipts to make another route
adopt an existing installation.

This revision implements hierarchical products/collections, native bundles,
coordinated Python wheels, hybrid applications, private/shared stores,
artifact-only installation, operation journals, and release export.
Windows/macOS code and native CI jobs are supplied; actual successful native
runs are required before advertising those targets as qualified.

Read [the product contract](docs/product-contract.md) for the complete semantics.
Project adoption and public catalog deployment are separate operations.

## Adopt the workspace profile

Merge `files/dev.sh`, `files/dev.ps1`, and `files/scripts/dev/` into a project,
then adapt `profiles/workspace/installation.toml.example`. Keep the project's
existing backends, manifests, lockfiles, development commands, and policies.
The detailed examples are the configurations in the
[Python](tests/fixtures/python-products/installation.toml),
[native](tests/fixtures/native-bundle/installation.toml), and
[hybrid](tests/fixtures/hybrid-product/installation.toml) fixtures. Their
application source is test data; use your project's actual source.

Declare buildable components first, then the products that compose them. Product
dependencies describe independently installed products; component dependencies
describe inputs assembled into one product. Use stable product IDs such as
`example-suite/tool` and an `example-suite` group containing the desired
children. Selecting the group performs the same operation over its complete
dependency closure.

Sibling checkouts must be declared through `[sources.NAME] path = "../project"`
and selected by the component's `source` field. Source paths are build inputs
only; portable installation consumes the packaged release. Public URLs are not
needed to build or verify these projects locally.

For an installation requiring no preinstalled language tools, declare reviewed
runtimes for each target. A runtime `path` bundles its pinned archive; a `url`
downloads it during explicit installation. Use bundled archives for a product
release intended to install offline. The first-stage helper runtime is supplied
separately to the bootstrap generator below. Private/shared ownership selects
where the product commands live; runtime bundling selects which bytes travel
with the release.

An adopter should run its own check/test hooks, package the individual products
and group, verify installation, and export the exact artifacts with evidence.
Use [the CI example](examples/workflows/ci-products.yml.example) for native
platform jobs. Updating an adopted template revision is explicit and preserves
project-specific adapters.

## Try individual products and a collection

Choose new destinations outside this repository:

```sh
python3 scripts/render_fixture.py product-workspace /tmp/example-products
cd /tmp/example-products
./dev.sh help
./dev.sh doctor
./dev.sh package --product example-suite/alpha --output /tmp/alpha-release
./dev.sh verify --artifact /tmp/alpha-release --install
./dev.sh install --artifact /tmp/alpha-release --prefix /tmp/example-product-store
./dev.sh package --product example-suite --output /tmp/collection-release
./dev.sh plan --artifact /tmp/collection-release --prefix /tmp/example-product-store
./dev.sh install --artifact /tmp/collection-release --prefix /tmp/example-product-store
./dev.sh inspect --prefix /tmp/example-product-store
/tmp/example-product-store/bin/alpha --self-test
```

The sample selects Python 3.14. Use that helper interpreter or intentionally
adapt its declared version for a compatible disposable test. PowerShell uses
the same arguments through `dev.ps1`; installed Windows commands are native
`.exe` launchers.

Windows native product commands receive VERSIONINFO before release hashes are
sealed. Installed launchers identify the product and command they launch, using
the product's numeric version and full prerelease ProductVersion. For example,
`0.1.0-beta` appears as `0.1.0.0` in PowerShell's numeric Version column and as
`0.1.0-beta` in the file's ProductVersion. Launchers remain owned, hash-checked
files during upgrades, rollback, and removal. Stamp executables before signing.

Inspect command selection without changing PATH:

```powershell
.\dev.ps1 commands --prefix "$env:LOCALAPPDATA\Aixand\products" --command alpha
```

Explicitly register a shared, user-owned installation on Windows:

```powershell
.\dev.ps1 commands --prefix "$env:LOCALAPPDATA\Aixand\products" --register-path --command-policy keep
.\dev.ps1 commands --prefix "$env:LOCALAPPDATA\Aixand\products" --register-path --command-policy prefer
```

`keep` preserves existing user PATH precedence and appends a missing command
directory. `prefer` moves that directory before other user PATH entries. Both
retain existing executables. System PATH entries can still take precedence;
the report shows the effective selection. PowerShell inspection uses a fresh
process without profiles; aliases, functions, and profile edits may override
that selection in a particular terminal. Installed versions come from product
receipts; competing native CLI versions are queried with a bounded `--version`
probe. Unsupported version probes are reported as unavailable.

`install`, `reinstall`, and `upgrade` also accept `--register-path` with the same
optional `--command-policy`. Library installation APIs and verification fixtures
never register global commands implicitly. Artifact-only consumers and generated
PowerShell bootstraps forward these same options. Private stores refuse PATH
registration.

The collection reuses the installed child release. Children keep independent
payloads, while the group records a tested release set. Removing the collection
preserves the child that was explicitly installed first:

```sh
./dev.sh uninstall --product example-suite --prefix /tmp/example-product-store --stopped
./dev.sh uninstall --product example-suite/alpha --prefix /tmp/example-product-store --stopped
```

## Source and private installation

```sh
./dev.sh install --product example-suite/alpha --prefix /tmp/source-products
./dev.sh install --product example-suite --prefix /tmp/source-products --dry-run
./dev.sh install --artifact /tmp/collection-release \
  --prefix /tmp/example-app/runtime --scope private --owner example-app
```

Source and artifact routes record different origins and cannot silently take
over one another's products. Shared defaults use the platform's per-user Aixand
data directory, with separate `source-products` and `products` stores. Commands
live in its `bin` directory; PATH registration is explicit. No shell profile or
user PATH is edited.

Private scope requires an explicit prefix/application owner. Its commands stay
inside that application's store. Software installation does not start services,
reuse existing credentials, or prepare models implicitly.

## SDK, native, and hybrid fixtures

The `python-products` fixture builds a library and CLI with an internal
dependency. SDK components can be packaged and checked independently:

```sh
./dev.sh package --component library --output /tmp/library-release
./dev.sh verify --artifact /tmp/library-release --install
```

Run these commands in a rendered `python-products` fixture. Its library consumer
proof creates no global commands. Schema-1 Rust library consumer verification
remains available through its original ecosystem adapter.

`native-bundle` runs a native command, companion executable, and resource.
`hybrid-product` runs a native executable that actually loads Python's shared
library and imports an SDK installed from the packaged wheelhouse.

## Artifact-only operation and progress

The portable consumer works without the source tree or `installation.toml`:

```sh
python3 -B scripts/dev/consumer.py install \
  --artifact /tmp/collection-release --prefix /tmp/portable-products \
  --request-id first-setup --events jsonl
```

Reuse a request ID with the same manifest, selection, operation, and origin to
resume an interrupted batch. Different inputs fail. Completed products are
reconciled before side effects. Logs go to stderr; events/final results go to
stdout.

Static `verify` executes no product commands. `verify --install` explicitly runs
declared checks in a disposable installation. `--expected-sha256` binds artifact
operations to an externally supplied manifest identity; hashes alone do not
authenticate a publisher.

Use `--report /absolute/path/verification.json` to save static or installation
evidence outside the immutable artifact. Export accepts that report only when
its manifest digest and target match. A static report does not claim runtime
qualification.

## Bootstrap and release handoff

The bootstrap generator needs a reviewed, relocatable CPython runtime descriptor:
target, HTTPS URL, SHA-256, executable, role, format, and optional strip count.

```sh
python3 scripts/dev/bootstrap.py \
  --runtime-descriptor /absolute/path/helper-runtime.json \
  --output /tmp/portable-installer
./dev.sh export-release --artifact /tmp/collection-release --output /tmp/release-handoff
```

The generated shell/PowerShell launcher verifies its runtime before executing
Python. The helper zip application is embedded and checked by digest. Shell
bootstrap needs curl, archive extraction, and a SHA-256 utility; Windows uses
PowerShell with ZIP extraction or system tar. The product route requires no
Python, uv, Node, or Rust on the user's command path.

The bootstrap test uses loopback delivery, a packaged interpreter, and a PATH
without Python. It does not qualify arbitrary upstream runtime archives or
replace clean-machine testing of an advertised distribution.

Release export contains `product-descriptor.json` and exact verified files under
`artifacts/`, with `publication: not-published`. It changes no destination or
channel pointer. Workspace release checks use a declared tag pattern, defaulting
to `{product}/v{version}`, and bind clean source inputs to the selected artifact.

The later installer integration can map these stable product IDs to
`installer.aixand.org/<product>/install.sh` and corresponding PowerShell routes.
The group and each child have their own selection and release descriptor.

For a handoff with installation evidence:

```sh
./dev.sh verify --artifact /tmp/collection-release --install --report /tmp/verification.json
./dev.sh export-release --artifact /tmp/collection-release \
  --report /tmp/verification.json --output /tmp/qualified-handoff
```

Releases record actual build tool versions, source identities, declared notices,
and a platform baseline. Set `workspace.baselines.<target>` to the minimum tested
`libc` (Linux) or `os-version` (macOS/Windows). A native package defaults
conservatively to its build host; a cross-target package needs an explicit
baseline. Installation checks the baseline before creating the store.

## Lifecycle and qualification

Upgrades are explicit and require a new version when bytes change. Reinstall
can repair an owned selection. Stateless individual products can roll back;
collection pins and installed consumers prevent incompatible changes.
Stateful rollback requires a migration-aware adapter.

Pruning retains current/previous payloads; actual prune/uninstall requires
`--stopped`. Persistent data, shared runtimes, and installer caches remain.
Do not infer safe database rollback or automatic service restart.

Run the normal template checks/tests. Native platform CI exercises the same
contracts on Windows/macOS. Record actual CI results separately from locally
executed Linux results.
